### Мотивация:
Добавление в проект позволит:
+ увеличить производительность системы
+ ускорить обработку запросов
+ снизить нагрузку на базы данных

### Предлагаемое решение
**Для проекта можно применить несколько подходов к кэшированию:**
1. клиентское
2. Refresh-Ahead или Cache-Aside
3. Write-Behind


**1. MES**
 + Не лишним будет клиентское кэширование MES и Internet Shop, т.к. все обновления интерфейсов происходят планово и перед нами стоит задача сократить время загрузки
 + Для страницы со списком заказов **рекомендуется Refresh-Ahead**. 
Т.к. принципиальными для системы являются актуальность данных и скорость их получения.

Из других систем кэширования **можно применить: Cache-Aside** - из-за его простоты, однако он не кажется лучшим вариантом, т.к. есть риск получить неактуальные данные.
+ **Read-Through** - выглядит не лучшим решением из-за возможности получить неактуальные данные, сложности настройки и риске ошибок из-за ограничений на модель
+ **Write-Behind** - так же не подходит нам, потому что может возвращать неактуальные данные, не решает проблемы с быстрым доступом к данным
+ **Write-Through** - **не рекомендуется**, т.к. хоть гарантирует консистентность, но может замедлять и без того медленное получение списка заказов
+ **Write-Around:** - **не рекомендуется**, т.к. решает задачи которые не стоят перед нами в текущем кейсе

**2. Internet Shop**
    Клиентское кеширование
    
**3. Shop Api**
    Рекомендуется **Write-Behind** - т.к. обеспечивается высокую производительность при записи

**4. CRM и CRM API**
+ Клиентское кеширование
+ Рекомендуется **Write-Behind** - обеспечивает быструю запись, в кейсе нет указаний на то что CRM часто запрашивает чувствительные к актуальности данные

**Стратегия инвалидации кэша**
Для проекта рекомендуется комбинация двух стратегий инвалидации:
для систем:
+ CRM API
+ Shop Api
использующих паттерн кэширования: Write-Behind - рекомендуется **инвалиадция на основе изменений** или **программная валидация**. 
Данные меняются из разных участков системы и мы должны гарантировать что в кэше только актуальные данные

+ **для MES API**, использующих стратегию Refresh-Ahead, рекомендуется стратегия инвалидации по ключу, это позволит нам обновлять только те данные кэша, в которых произошли изменения

**Для интерфейсов CRM и Internet Shop**, для которых применяется клиентское кэширование, рекомендуется **Инвалидация основанная на запросах**
**Для MES** - рекомендуется **инвалиадция на основе изменений**

Для проекта **не подойдут варианты** инвалидации кэша:
**Временная инвалидация**, т.к. у нас все данные изменяются по сценариями, которые происходят в системе. Временная инвалиадция не даст гарантии актуальности данных в кэше
